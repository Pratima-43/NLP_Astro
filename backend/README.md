# AstroVerse backend

FastAPI backend for the Next.js frontend. Three source-grounded modules — Numerology, Vedic
Astrology and Palmistry — plus an integration layer (chatbot and combined report) that compares
their claims. Every interpretation is generated by Groq **only** from knowledge-base records, and
every cited record ID is validated server-side.

## Structure

```text
backend/
  app/
    api/            router composition
    auth/           accounts (scrypt, signed tokens), password reset/change, account deletion, Supabase JWTs
    core/           settings, SMTP email, shared Groq client (JSON mode, rate-limit retry, response cache)
    db/             SQLAlchemy models, sessions, idempotent seed sync
    modules/
      numerology/       calculations (guide §3–6), KB retrieval, interpretation + synthesis
      vedic_astrology/  Swiss Ephemeris chart engine, Parashari analysis, KB builder, reading
      palmistry/        MediaPipe landmarks, crease detection, line/mount measurement, KB builder, reading
      integration/      cross-system claim pool, chatbot, combined report
  alembic/          migrations 0001–0005 (numerology, multi-system, users, account security, RLS)
  training/         optional palm-line U-Net training/export script
  tests/
```

## Run locally (Windows PowerShell)

```powershell
cd backend
py -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
Copy-Item .env.example .env          # then set GROQ_API_KEY
uvicorn app.main:app --reload --port 8000
```

With `APP_ENV=development` and `AUTO_CREATE_TABLES=true`, tables are created and all three
knowledge bases are synced from their seed files on startup. Swagger UI: `http://localhost:8000/docs`.

Optional: `python prewarm_numerology_cache.py` pre-generates the 36 person-agnostic numerology
component readings so first reports are instant.

## Supabase (PostgreSQL)

1. Supabase → **Connect** → copy the **Session pooler** URI into `DATABASE_URL`
   (`postgresql://postgres.<ref>:<password>@aws-0-<region>.pooler.supabase.com:5432/postgres`).
   The direct `db.<ref>.supabase.co` host is IPv6-only and times out on many networks.
2. Set `AUTO_CREATE_TABLES=false`, then run `alembic upgrade head` and `python seed_knowledge.py`.
3. Migration `0005` enables row level security on every table. The backend connects as the table
   owner and is unaffected, while Supabase's public REST API (reachable with the anon key) can read nothing.

`alembic check` reports no drift between the models and migrations. To add a schema change: edit
`app/db/models.py`, run `alembic revision --autogenerate -m "..."`, review the file, then `alembic upgrade head`.

## Accounts and email

The app has its own accounts by default: email + password (scrypt hash), 7-day signed tokens, and
throttled logins. Changing or resetting a password revokes every older token.

- **Forgot password**: `/forgot-password` emails a single-use link (valid `PASSWORD_RESET_MINUTES`,
  default 30) to `/reset-password?token=…`. Only the SHA-256 of the token is stored. The response is
  identical whether or not the email exists.
- **Email delivery** needs `SMTP_HOST`/`SMTP_PORT`/`SMTP_USERNAME`/`SMTP_PASSWORD`/`SMTP_FROM`
  (e.g. Gmail with an app password). Without SMTP in development, the email text including the reset
  link is printed in the backend console.
- **Settings → Account**: change password, delete account (removes the user and all their readings).
- **Notification preferences** are stored on the user and control the in-app bell and security emails.

Optional **Supabase Auth**: set `SUPABASE_URL` (backend) and `NEXT_PUBLIC_SUPABASE_URL` /
`NEXT_PUBLIC_SUPABASE_ANON_KEY` (frontend). Login, signup and password reset then go through
Supabase, and Supabase users are mapped to `users` rows with id `sb_<uuid>`. Supabase's built-in
mailer only delivers to your project's team members, so configure custom SMTP in Supabase
(Authentication → Emails) before letting other people sign up.

## API

| Method | Path | Purpose |
|---|---|---|
| POST | `/api/v1/auth/signup`, `/auth/login` | Create account / sign in → access token |
| GET, PUT | `/api/v1/auth/me`, `/auth/profile` | Current user; update profile and notification preferences |
| POST | `/api/v1/auth/password/forgot`, `/auth/password/reset` | Email a reset link; set a new password from it |
| POST | `/api/v1/auth/password/change` | Change password (needs the current one) |
| DELETE | `/api/v1/auth/account` | Delete the account and all its data |
| POST | `/api/v1/auth/premium/redeem` | Redeem a coupon (`ASTROFREE`) |
| POST | `/api/v1/numerology/calculate` | Moolank, Bhagyank, Namank, Personal Year + reading |
| GET | `/api/v1/astrology/geocode?q=` | Place → coordinates + time zone |
| POST | `/api/v1/astrology/chart` | Sidereal chart, dashas, yogas, transits + reading |
| POST | `/api/v1/palmistry/analyze` | multipart `image`, `hand` → lines, mounts, overlay + reading |
| POST | `/api/v1/integration/chat` | Answer from all three readings with module contributions |
| POST | `/api/v1/integration/report` | Theme-by-theme cross-system comparison |
| GET | `/api/v1/{numerology,astrology,palmistry}/latest`, `/api/v1/integration/status` | Saved readings |

## Method notes

**Numerology** follows `Numerology Guide.pdf` exactly: Moolank from the birth day (compound day kept),
Bhagyank from all date digits, Namank with the Chaldean table (spaces/punctuation ignored, digits at
face value, other characters rejected), Personal Year = reduced day + month + target-year digits.
Records keep their evidence layer (component-specific, compound, general, context) as the guide requires.

**Vedic Astrology** uses pyswisseph with the Lahiri ayanamsa, whole-sign houses and mean nodes.
Dignities, natural friendships, combustion, navamsa/vargottama, a transparent strength score,
yogas (Gaja Kesari, Pancha Mahapurusha, Raja/Dhana/Viparita, lunar yogas, Mangal Dosha, Neecha
Bhanga), Vimshottari maha/antardashas, Sade Sati and life-domain scores are all rule-based and
return their factors. The knowledge base (`knowledge_base/build_seed.py`) paraphrases classical
significations (BPHS, Phaladeepika, Brihat Jataka); entries are labelled `classical_paraphrase`.

**Palmistry**: MediaPipe Tasks HandLandmarker (the legacy `mp.solutions` API is removed in current
releases) → canonical palm frame → Sato ridge + black-hat crease map → minimum-cost tracing of each
principal line in landmark-anchored corridors → measurements (length, depth, curvature, breaks,
forks, endpoints) → named conditions → claims. Palm side vs back of hand is checked from the 3D
landmark normal. The knowledge base quotes Cheiro's *Palmistry for All* (Project Gutenberg #20480)
verbatim; mortality/medical passages were excluded.

No public pretrained palm-line weights exist. `training/train_palm_unet.py` trains a lightweight
U-Net (MobileNet encoder, BCE + Dice) on CC BY 4.0 Roboflow palm-line segmentation sets (e.g.
Palm-Detection-1) warped into the same canonical frame, and exports
`app/modules/palmistry/models/palm_lines_unet.onnx`; with `onnxruntime` installed it is blended in
automatically.

**Integration**: claims from the three saved readings are tagged with shared themes and weighted by
evidence strength. A module's contribution to an answer = summed weight of its *cited* claims ÷
total cited weight, computed server-side, not by the model.

All outputs are traditional interpretations, not scientifically validated predictions.

## Groq limits

Free-tier `openai/gpt-oss-120b` allows 8,000 tokens/minute. The client waits out 429s, uses low
reasoning effort, and caches person-agnostic readings in `llm_cache`. A higher tier or a model with
larger limits makes first-time readings faster.
